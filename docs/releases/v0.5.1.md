## Scope and compatibility

- `runtime.scheduler.decode_burst_tokens` and fairness timeslicing no longer
  slice requests on the stateless legacy `Generate()`/`GenerateWithImages()`
  executor path (logprobs, `response_format`, images without phased state).
  Such requests run their whole decode budget in one executor pass. KV-resumable
  phased decode keeps the burst cadence. Configuration is unchanged: the knob
  is safe at any value on this version; older binaries must keep it `0`.
- `fairness.service_tokens` is charged once per executor pass (a stray
  duplicate charge on the legacy path was removed).
- `inferflux_prefix_hits_total`, `prefix_misses_total`, `prefix_matched_tokens_total`
  and `prefix_partial_hits_total` now record radix-trie consultations from
  scheduler prefill admission. They are trie-level signals; accepted reuse
  remains `inferflux_kv_prefix_reuse_total` and per-request cached-token usage.
  `docs/MONITORING.md` states the semantics.

### Deployment checkpoint (2026-10-19)

The serving unit already runs the fix via the staged trusted-main hotfix bundle
`main-59688833ec2a` (source `59688833ec2a7cb99bd69919db8e06b2c0c86b44`, binary
SHA-256 `1784ed02451e586b8757eb569a68ff9a9e0c92c360113be38ee7da6310c5c1d7`),
deployed with a recorded one-step rollback. Post-deployment qualification with
`decode_burst_tokens=8`: the incident reproduction shape (logprobs,
`max_tokens=64`) completes in a single prefill with coherent output in under a
second, and `json_object` requests return complete valid JSON; a Victor-scale
synthetic request (9.3k prompt tokens, logprobs, `max_tokens=1024`) completed
in 6.7 s end-to-end on the mitigated v0.5.0 predecessor binary. The cutover
and rollback details live in the private-side deployment record
(`deployment-1792426383936066073`, aiserver1). Publishing v0.5.1 gives the same code an immutable
tag and packages; swapping the running bundle for the tag-qualified build is an
operator decision, not required for correctness.

Follow the [release process](../ReleaseProcess.md). Standard Linux release
archives are CPU-only; a dual-GPU deployment needs a separately recorded mixed
build from the exact published source, as done above.
